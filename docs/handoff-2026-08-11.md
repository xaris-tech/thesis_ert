## Why this session happened

The prototype had failed its baseline stability gate on every tuning preset
since 2026-07-02, and the goal was to improve output quality. The causes turned
out to be configuration and software, not fundamentals. Three findings drove
most of the work:

1. **The UI never saved anything.** `DebugController` computed reconstructions
   in memory and discarded every frame. No logger existed anywhere in
   `tree_ert/`. Every UI session ever run, including the July tuning work, left
   no data behind.
2. **The ADC was throwing away 8x of its resolution.** `GAIN_ONE` against ~13 mV
   signals meant a median measurement used 106 of 32,768 counts, and
   quantisation error alone exceeded the 2% stability limit on 9.8% of
   measurements. Quantisation is a fixed grid, so averaging could never fix it.
3. **The reconstruction filter deleted the defect signal.** Any pair moving more
   than 0.05 kOhm from baseline was overwritten with its baseline value. A
   drilled hole moves nearby pairs most, so the filter was most likely to erase
   the strongest evidence.

## State of the work

### Implemented and tested (88 tests pass)

- CSV logging in the UI acquisition path, with `specimen` and `stage` required
  and written into every row and every filename
- `--specimen` / `--stage` CLI flags, required with `--log`
- Voltage channel at `GAIN_EIGHT`; `V_RANGE` guard retied to the PGA full scale
- Large deltas reported as `large_delta_pairs`, never masked
- Serial port auto-detection that excludes Bluetooth devices
- Electrode material changed to stainless steel screws throughout the docs

### Decided but NOT implemented

- **Scan loop restructure** — configure injection once per injection pair and
  hold it while the voltage muxes sweep, instead of tearing the injection path
  down 216 times per frame. This is the change most likely to fix the remaining
  drift. See ADR 0004. Note that
  `test_switching_goes_idle_before_mux_addresses_change` asserts the current
  per-measurement teardown order and must be updated alongside it.
- **43-sample continuous-mode averaging** for 60 Hz mains rejection — pending
  the battery test below.
- **Signal-referenced stability gate** — replace the invented
  `MAX_BASELINE_RELATIVE_RMS_PERCENT = 2.0` with a value derived from the
  measured phantom target response. The current threshold has no justification
  anywhere in the repo and has never been passed.
- **Absolute reconstruction with a measured trunk model** — needed for standing
  trees, which have no time baseline. Currently only difference reconstruction
  exists. See ADR 0001 and methodology 3.13.
- **Feature extraction and classifier** — no code exists yet. See ADR 0003.

## Do these next, cheapest first

1. **Battery test — 2 minutes, no code.** Run one baseline capture with the
   laptop charger unplugged, then the same plugged in. Compare relative RMS. A
   drop means mains coupling is real and the 43-sample fix is worth building.
2. **Flash the updated firmware and re-baseline on the phantom.** The
   `GAIN_EIGHT` change alone should visibly lower relative RMS. Keep the old
   number for comparison — `docs/drift-tuning-presets.md` has the history, but
   all of it predates these changes and is not directly comparable.
3. **Buy 304/316 stainless steel screws** to replace the iron nails.
4. **Restructure the scan loop** (1–2 hrs, then re-verify on the phantom).
5. **Phantom current sweep** — DAC 100/150/200/300, recording drift against the
   5th-percentile measurement voltage, to pick the operating current.

Items 1 and 2 should happen before anything else, because every later change
needs a clean before-measurement to compare against.

## Traps

- **`tree_ert_app.py` is a desktop app, not a web server.** There is no dev
  server. Run `.venv/bin/python tree_ert_app.py --demo` to use it without
  hardware.
- **Tests must not write into `phase3a_logs/`.** Controller tests use
  `default_settings()` which sets `log_enabled=False`. Keep it that way.
- **`docs/archive/` is provenance only.** Do not wire or build from it.
- **`ert.py` and `pyeit_analyzer.py` are legacy Phase 2 tools**, still tested and
  still useful for export analysis. They are not the current path, and they
  parse a different serial format (`SCAN:`). Do not merge the two protocols.
- **When a doc contradicts an ADR, the ADR wins** and the doc needs updating.
- Five superseded firmware directories were deleted. Only
  `esp32s3-phase3a-unified-arduino` is current;
  `esp32s3-hcp-test-arduino` remains as a bench tool for the dummy-load step.

## Could not verify in this session

- **No hardware was attached.** Every code change is verified only by unit tests
  and the demo acquisition path. Nothing here has been confirmed against a real
  ESP32-S3, and the firmware has not been compiled or flashed.
- **pyEIT was not inspected for an absolute solver.** It installs from
  `requirements.txt` but the specific API for absolute reconstruction was never
  confirmed. Check before committing to the approach in methodology 3.13.
- **The frame-time estimates in ADR 0004 are calculated, not measured.** Adding
  a timestamp to the `FRAME` and `END` serial lines would turn them into fact.
- **The mains-hum hypothesis is untested.** It is a plausible explanation for
  part of the drift, not a demonstrated one.

## Suggested skills for the next session

- **`debugging-and-error-recovery`** — for working through the remaining drift
  systematically once bench measurements come back, rather than guessing at
  causes. The tuning history shows how easily this turns into knob-twiddling.
- **`test-driven-development`** — the scan-loop restructure changes firmware
  behaviour that only source-level tests can check. Write the new assertion
  before changing the loop.
- **`grilling`** with **`domain-modeling`** — if new design questions open up,
  particularly around absolute reconstruction or the classifier, both of which
  are decided in principle but entirely unbuilt. This is how ADRs 0001–0004 and
  the `CONTEXT.md` vocabulary were produced.
- **`source-driven-development`** — before building absolute reconstruction,
  since it depends on pyEIT API details that were never verified here.
